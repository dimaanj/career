Релиз «зелёный» только когда все новые поды реально готовы

smn-spiderman · Argo CD · все сервисы SMN

Сейчас

Argo CD показывает Healthy, а логин отдаёт 404 на otp/settings, пока руками не перезапустишь api-gateway.

«Healthy» сейчас значит «процесс отвечает на /actuator/health», а не «сервис может обслуживать запросы».

Хотим

Под получает трафик, а приложение становится Healthy, только когда новая версия реально готова: БД/Redis доступны, а у gateway загружены маршруты критичных сервисов.

Медленный старт не убивается liveness. Hook test-connection ловит неготовность и не блокирует следующий sync.

Готов принимать трафик?

kubelet → readinessProbe
Сейчас/actuator/health, общий статус. У gateway он не знает про маршруты: Ready даже без маршрутов к otp/settings.
Будет/actuator/health/readiness = readinessState + критичные зависимости: db (JPA), redis (otp, gateway). У gateway добавляется openApiRoutes: маршруты критичных сервисов загружены.

БудетТо же, но новый под попадает в Service только когда действительно готов. До этого трафик обслуживает старый под.

Контрольная проверка

Приложение зелёное

Argo CD · Synced + Healthy
РезультатЗелёный = все новые поды Ready по честной readiness, hook прошёл. Родитель smn-spiderman честно зелёный, только если платформа включит health check для Application.

Постоянно после старта · livenessProbe

/actuator/health/liveness, timeout 3 с. Проверяет только «процесс жив», без БД, Redis и маршрутов: падение зависимости не должно рестартить поды, только выводить их из трафика (readiness).

api-gateway: как будет работать старт

Шаг 4 этапов релиза, развёрнутый для gateway

1. Под стартовал

startupProbe OK (liveness)

2. Тянет openapi.yaml

у 9 сервисов, с connect/read таймаутом, повтор каждые 30 с (было 5 мин)

3. Критичные загружены?

otp-validator, settings, user-profile, support-panel (+ prof-events). Нет → readiness DOWN, трафик идёт в старый под

4. Ready

под в Service. Некритичные дотянутся следующим refresh, не блокируют

5. PostSync

/actuator/gateway/routes содержит маршруты всех критичных сервисов, иначе hook падает

Риск

Критичный сервис лежит во время релиза: новый gateway не станет Ready, старый продолжит работать, раскатка упрётся в progressDeadlineSeconds. Это лучше, чем 404, но нужен алерт.

Решить

Критичный сервис упал после релиза: маршруты удаляются через 15 мин, и gateway становится NotReady целиком. Варианты: readiness проверяет «хотя бы раз загружено» или увеличить таймаут удаления.
